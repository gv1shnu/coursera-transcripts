Hello, in this video, you'll learn about compound indexes. In particular, we'll cover what compound indexes are and how to create them. You'll also learn how to use a compound index to sort query results and cover queries. A compound index is an index on multiple fields.

Compound indexes can also be multi key indexes if they include an array field with the limitation of only one array field per index. Compound indexes can cover and support queries that match on the prefix of the index fields. Let's look at an example to explain this point in more detail. The Customer's Collection contains details about customers, such as their name, their birth date, and whether they're active.

We use the Create Index method to create an index on the active and birthdate fields. Any query that contains active or sourced by active can use the index because active is the first field or prefix in the index. Queries that do not include the index prefix can't use the index even if they include other fields in it. This is because indexes are ordered structures.

The order of the fields in a compound index matters. In general, when we're defining the list of fields and compound indexes, we want fields tested for equality first, followed by fields that are used for sort or range. Additionally, if we require specific sorted result in our queries, the sort order of the field values in the index also matters to avoid in-memory sorts. Let's examine this in more detail.

Equality predicates test exact matches on a single value, like we do when searching for a specific active customer or birth date value. Those fields should be placed first in a compound index. This reduces the processing time for a query and retrieves fewer documents. Sort predicates determine the order of results.

For instance, we can sort by name and ascending order or by birthday and descending order. The sort field should be included in the index after the equality fields. This is because once we select a specific value for the first field, the other field values will be in order. The sort order of these field values in the index is important if the query results are sorted by more than one field, and they mix sort orders.

That is, some fields are in ascending order and other fields are in descending order. Range filters scan fields, as shown in this example, with birth date values between 1977 and 1995. Note, in general, we recommend that range and sort should be placed after equality in the index to avoid in-memory sort or filtering. Let's review this with an example.

We'll use a database called Sample Analytics and the Customer's Collection. We want to run this query on the Customer's Collection to find all the documents where the birth date is greater or equal to January 1977 and the account ID is active. Then sort the results by birthday and descending order and the name in ascending order. The results of this query are returned in order based on birthday, descending and name ascending.

All results match the filter criteria. Let's use the same query as before and execute the explain method on the query to understand what MongoDB is doing to retrieve the data. First, MongoDB performs an index scan over one of the existing indexes. In this case, it's the single field index on birthday.

Then it executes a fetch that uses a filter looking for the active customers. Finally, it performs a memory sort based on birthday and descending order and name an ascending order. We can improve the performance of the query by creating an index that better supports it. To do this, we use the Create Index command and order the fields according to the Guideline of Equality first, followed by sort.

We include the active field first because we query by using equality on this field, birthday and name are placed next because we sort by these fields. The sort order of these fields matters because they mix descending and ascending orders of the query. We'll sort birthday and descending order with negative 1 and name an ascending order with 1 in the index following the same pattern as in the query. We can also sort them with birthday and ascending order and name a descending order, both indexes will work.

For this example, we'll use the first version with the birthday set to negative 1 and the name set to 1. We also have a range query on birthdate, but this field is already included in the list. Perfect, the compound index is created. To verify if the new index is being used, we'll run the explain query again.

The winning plan shows the new index that we created is being used in the index scan. A fetch stage is performed based on the index results, resulting only in the necessary documents from the collection. In most cases, the fetch stage can be avoided if we only project fields that are in the index. Let's go through an example of a compound index that covers a query.

To the previous query, we'll add a projection in the find command to return only name and birth date, excluding the default underscore ID field. Now, the documents returned by the query only have those fields. Now with this new query, let's use the explain method again to review the execution plan. Great, this output shows that the compound index is being used and there is no fetch stage because the index covers the projection.

This execution is faster than the one with no projection because there's no extra step to read the documents. If a query projects additional fields that we don't use to filter or sort by, we can include those fields at the end of the field list when we create the index. This way, we use the index to cover the query and avoid fetching the documents. Excellent work.

In this video, you learned about compound indexes and how to define the order of fields in the index based on query equality, sort, and range predicates. You also learn how to use the Create Index command to create a compound index and the explain method to confirm that the compound index that we created was being used. Finally, you'll learn how to cover a query with the index to avoid the fetch stage.
