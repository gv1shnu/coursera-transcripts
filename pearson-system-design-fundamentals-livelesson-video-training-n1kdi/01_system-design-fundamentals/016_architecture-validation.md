So far, we discussed architecture as an act of decomposition. You take a big nebulous idea, you break it down into the components of the system. But architecture has no value on its own. The system needs to put these things together at runtime to fulfill some business need.

So next is composition. How do we compose these components together into the required behaviors? Composition is intimately related to validation. How do we know the composition of the building blocks of the architecture is actually any good?

How do we know we have a valid design? Now fundamentally, at runtime, we're going to have interaction between these components. This interaction needs to satisfy the requirements of the system. We already discussed that you can express, and you should express the requirements as use cases.

You want to focus on the required behavior, not the required functionality.
